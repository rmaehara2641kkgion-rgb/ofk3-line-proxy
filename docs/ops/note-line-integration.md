# 配送管理アプリにLINE連携を実装した話 — 85名のドライバーにワンクリックで配車表を届けるまで

## はじめに

私はAmazonラストマイル配送の拠点（DSP）で管理業務をやっています。日々の業務で使う社内ツールを自分で開発しているのですが、その中で一番「作ってよかった」と感じているのがLINE連携機能です。

この記事では、配送管理アプリにLINE Messaging APIを組み込んだ技術的な構造と、実装中に起きたエピソードを書きます。

---

## そもそも何を解決したかったのか

毎朝、管理者がやる作業がありました。

1. Amazonのアサインデータ（Excel）を開く
2. ドライバーごとのコース番号・配達数・エリアを確認
3. グループLINEに手打ちで配車表を投稿
4. 個別の問い合わせに対応（「今日のコースどこ？」「荷物何個？」）

85名のドライバーに、毎朝これをやる。しかもシフトは日替わり。

「Excelを取り込んだらLINEに自動で飛ぶようにすればいいのでは？」

これがLINE連携を作ったきっかけです。

## 全体のアーキテクチャ

```
┌───────────────────────────────┐
│  ブラウザ（index.html）       │
│  ・Excel取込・UI・配車表生成  │
│  ・LINE送信リクエスト発行     │
└──────────┬────────────────────┘
           │ POST /proxy
           │ { to: "Uxxxx", messages: [...] }
           ▼
┌───────────────────────────────┐
│  Renderサーバー               │
│  render-webhook-server.js     │
│  ・PROXY_SECRET認証           │
│  ・LINE Push API 中継         │
│  ・Webhook受信（友だち追加）  │
│  ・プロフィール写真取得       │
│  ・配送MAP画像プロキシ        │
└──────────┬────────────────────┘
           │ Bearer Token
           ▼
┌───────────────────────────────┐
│  LINE Messaging API           │
│  ・Push Message（個別送信）   │
│  ・Get Profile（写真・名前）  │
└───────────────────────────────┘
```

ポイントは**ブラウザから直接LINE APIを叩かない**こと。Channel Access Tokenをフロントエンドに置くわけにはいかないので、Node.jsのプロキシサーバーを中継しています。

## 実装の構造を詳しく

### 1. ドライバーとLINEアカウントの紐付け

ここが最初の壁でした。LINEのUser IDはBot側からしか取得できません。ドライバーにBotを友だち追加してもらって、followイベントからUser IDを取得する仕組みです。

```
ドライバーがQRコードでBot追加
  ↓ followイベント
Webhook受信（/webhook）
  ↓ event.source.userId を取得
ウェルカムメッセージ送信
  ↓
管理者がマスタ画面でドライバー名とUser IDを紐付け
```

実際のコードはシンプルです。

```javascript
// Webhook受信
app.post('/webhook', async (req, res) => {
  const events = req.body.events || [];
  for (const event of events) {
    if (event.source && event.source.userId) {
      if (event.type === 'follow') {
        await sendWelcomeMessage(event.source.userId);
      }
    }
  }
  res.status(200).json({ status: 'ok' });
});
```

最初はドライバーにTransport IDをBotに送信してもらって自動紐付けする予定でした。でも「LINEにIDを打ち込んで」と言っても半分くらいの人が戸惑う。結局、管理者がマスタ画面で手動紐付けする方式に落ち着きました。

**教訓: 現場のドライバーに複雑な操作を求めてはいけない。**

### 2. プロキシサーバー（LINE送信の中継）

フロントエンドからの送信リクエストを受けて、LINE Push APIに中継します。

```javascript
app.post('/proxy', async (req, res) => {
  // PROXY_SECRET で簡易認証
  if (PROXY_SECRET && req.headers['x-proxy-secret'] !== PROXY_SECRET) {
    return res.status(403).json({ status: 'error', message: 'Forbidden' });
  }
  
  const { to, messages } = req.body;
  const target = to === '__admin__' ? ADMIN_LINE_ID : to;
  
  await axios.post('https://api.line.me/v2/bot/message/push', {
    to: target,
    messages: messages
  }, {
    headers: {
      'Authorization': 'Bearer ' + CHANNEL_ACCESS_TOKEN
    }
  });
});
```

`to === '__admin__'` というのは、管理者宛ての送信を簡略化するための仕組み。フロントエンドは管理者のUser IDを知らなくても `__admin__` と指定すれば届きます。

### 3. フロントエンド側の送信処理

ブラウザ側では `getProxyHeaders()` という共通ヘッダー関数を作って、全26箇所のfetchに配線しました。

```javascript
function getProxyHeaders() {
  var h = { 'Content-Type': 'application/json' };
  var secret = localStorage.getItem('proxySecret');
  if (secret) h['x-proxy-secret'] = secret;
  return h;
}
```

1箇所ずつ手で書き換えたので、正直つらかった。でもセキュリティのためです。

### 4. 配送MAPの送信（一番苦労した部分）

テキストだけなら簡単ですが、配送MAPを画像で送りたかった。ドライバーのLINEに地図付きで届けば、配送エリアが一目でわかる。

問題は、LINEのPush Messageで画像を送るには**公開URLが必要**ということ。ブラウザで生成したLeaflet地図のスクリーンショットをそのまま送れない。

解決策: Google Static Maps APIで画像URLを生成し、Renderサーバー経由でプロキシ。

```
ブラウザ → 配送先の緯度経度リストを生成
  ↓
Renderサーバー /static-map にリクエスト
  ↓
Google Static Maps API で画像URL生成
  ↓
LINE Push Message の imageUrl にセット
```

ドライバーのスマホで受信した地図は、スワイプで拡大・移動できます。ピンの色も「未配達: 赤」「完了: 緑」「現在地: 青」で分けました。

## LINE連携でできるようになったこと

実装が進むにつれて、LINE連携の用途がどんどん広がりました。

| 機能 | 送信先 | 内容 |
|------|--------|------|
| **配車表の一斉送信** | 全ドライバー+管理者 | コース番号・エリア・配達数・終了予測+MAP |
| **点呼リマインド** | ドライバー本人 | 着車5分前に「点呼してください」 |
| **点呼未完了通知** | 管理者7名 | 着車時間超過の未完了ドライバー一覧 |
| **メンター停止アラート** | 管理者7名 | 走行中のメンター停止を30分毎監視 |
| **住所・地図送信** | 個別ドライバー | 配送先住所+スワイプ可能な地図 |
| **請求通知** | 個人事業主ドライバー | 月次請求金額+請求書PDF |
| **DNR通知** | 個別ドライバー | 未受領申告の詳細 |
| **一斉メッセージ** | 全ドライバー | 業務連絡 |

最初は「配車表を送る」だけだったのが、気づけば8種類の通知になっていました。

## 実装中のエピソード

### エピソード1: 「LINEの写真が表示されない」

マスタ管理画面にドライバーのLINEプロフィール写真を表示する機能を作ったとき、取得はできるのに画像が表示されない。

原因は**CORS**。LINE APIから返ってくるプロフィール画像URLは `profile.line-scdn.net` で、ブラウザから直接読み込めない。

解決策として、プロフィール画像URLだけを取得してimgタグのsrcに入れる方式にしました（画像自体はLINEのCDNから配信されるので、直接参照は可能。問題はfetchで取ろうとしたときだけ）。

### エピソード2: 「同じ人が2人いる」

LINE連携を進めていくと、ドライバー名の不一致問題が浮上しました。

- シフト表: 「晴樹 藤永」
- Amazonアサイン: 「晴樹 藤永晴樹 藤永」

同一人物なのにシステム上は別人扱い。LINE IDは片方にしか紐付かない。

これをきっかけに「名前解決エンジン」（resolveDriverKey）を作りました。8段階のアルゴリズムで、入力名を正キーに自動変換する仕組みです。別名マップ → サフィックス除去 → 空白除去一致 → 姓名反転 → TID逆引き……と段階的にフォールバックしていく。

さらに「同一人物候補UI」を作って、検出された重複ペアを管理者がワンクリックで統合できるようにしました。LINE IDやTransport IDは自動的に正キー側に移行されます。

**教訓: LINE連携を入れると、データの品質問題が可視化される。**

### エピソード3: 「テンプレートリテラルが使えない」

開発中にEdgeのIEモードで動かす必要があると判明。IEモードではバッククォート（テンプレートリテラル）が動かない。

すでに書いたコードを全部文字列連結に書き換える羽目になりました。`'Hello, ' + name + 'さん'` の世界です。16,000行以上のHTMLファイルで。

今でもこの制約は守っています。新しいコードを書くたびに「バッククォート禁止」を意識する。地味だけど、現場のPC環境に合わせるのは大事です。

### エピソード4: 「メンターが止まってることに気づけない」

Amazon配送ではメンター（安全運転監視アプリ）の起動が必須です。でも走行中に止まってしまうことがある。管理者がVRMの画面をずっと監視するわけにもいかない。

そこでActivepiecesで30分ごとにVRM APIを叩いて、前回Activeだったドライバーが消えたら「停止した」と判定してLINE通知する仕組みを作りました。

ここで問題になったのが**重複通知**。30分ごとに実行するので、同じドライバーに何度も通知が飛んでしまう。

解決策: GASスプレッドシートに通知済みリストを永続化。ActivepiecesのCode内からGASにGETリクエストを投げてチェック＆記録する方式にしました。POSTだとGASが302リダイレクトしてしまうので、全部GETパラメータで送るという力技。

## 技術スタック

一応まとめておきます。

- **フロントエンド**: 単一HTML（16,900行）+ TailwindCSS
- **バックエンド**: Node.js（Render無料枠）
- **データベース**: Google Apps Script + スプレッドシート
- **メッセージング**: LINE Messaging API
- **地図**: Leaflet.js + Google Maps Static API
- **Excel解析**: SheetJS（xlsx.js）
- **QR認証**: html5-qrcode
- **OCR**: Tesseract.js
- **自動監視**: Activepieces

「16,900行の単一HTML」は正気じゃないと思われるかもしれません。実際、たぶん正気じゃないです。でもこの構成にはメリットがあって、GitHubにファイルを1つアップロードするだけでデプロイが完了する。現場の管理者が「なんかおかしい」と言ったら、すぐ直してすぐ反映できる。

## 運用してわかったこと

### 1. LINEは「見てもらえる」

社内メールやSlackと違って、LINEは通知が確実に届く。ドライバーはスマホを常に持っているので、配車表も点呼リマインドも見逃されない。開封率はほぼ100%。

### 2. 通知は「情報量」と「タイミング」

最初は配車表をテキストで送っていましたが、地図付きにしたら「わかりやすい」とフィードバックをもらいました。逆に、情報を詰め込みすぎると読まれない。

点呼リマインドは「着車5分前」がベスト。10分前だと「まだ大丈夫」と思われ、1分前だともう間に合わない。

### 3. 紐付けの運用コスト

85名全員のLINE紐付けは1日では終わりません。ドライバーが出勤するたびに「Bot追加してください」と声をかけて、少しずつ進めました。3週間くらいかかった。

新人が入るたびに紐付け作業が発生する。これは今のところ手動です。自動化したいけど、現場のフローに組み込むには人間の声かけが一番確実。

## おわりに

LINE連携は、技術的には「APIを叩いてJSONを送る」だけのシンプルな仕組みです。でも、現場に導入すると想像以上に多くの問題が出てくる。名前の揺れ、ブラウザの互換性、通知のタイミング、紐付けの運用コスト。

それでも「朝のアサイン確定後、ボタン1つで85名全員に配車表と地図が届く」という体験は、作ってよかったと心から思えます。

配送管理のDXはまだまだやれることがある。次は退職者管理の自動化と、ドライバー能力DBのGAS同期を進める予定です。
