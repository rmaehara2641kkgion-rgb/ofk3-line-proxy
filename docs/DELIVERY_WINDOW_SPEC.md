# 配送時間帯 スキャン連動読み上げ — 照合仕様 (Phase 2)

状態: 仕様案 v0.1 / 実装: `delivery-window-core.js`, `delivery-window-voice.js` / テスト: `tests/delivery-window-core.test.mjs`
本番未反映。`index.html` は未変更。実データはリポジトリに含めない。

## 1. 原則

1. 時間帯は「確認できた」ときだけ読み上げる。それ以外は `確認できません！`。
2. SearchResults の時間欄が空欄でも「時間指定なし」とは判定しない(空欄は常に「確認できません」)。「時間指定なし」になるのは §4.1 の確定ルール(8:00〜22:00)だけ。
3. エリミと SearchResults が矛盾したら、どちらも正とせず矛盾として記録し、読み上げない。
4. 日付が不整合なデータは、検証が終わるまで読み上げない。
5. 部分一致で別荷物を拾わない。判断に迷う入力は読み上げない。

## 2. 入力

### SearchResults CSV (`parseSearchResults`)
- UTF-8 (BOM可) / CRLF・引用符・セル内改行に対応。
- 必須列: `Tracking ID`, `Scheduled Delivery Start Time`, `Scheduled Delivery End Time`, `Promised Delivery Date`。1つでも欠けたら取込拒否(欠落列名を返す)。
- 任意列: `Last Updated Time`(最終更新の表示に使用)。その他の列は無視。
- Tracking ID は半角化・trim・大文字化。空IDの行は件数のみ数えて捨てる。

### エリミ Excel (`parseElimiCycleSheet`) — 対象は「エリミネーション報告」のみ
- `Cycle<N>` 見出しセルの列ごとにセクションを認識し、直下を区分見出し、その下の `トラッキングID`/`TRID` 行をID列とする。
- 日付セル(`日付`の右)を基準日(reportDate)として読む。文字列・Excelシリアル・Date対応。
- ID形式外のセルは `invalidCells` に数える。
- 他シート(未配報告・DFK2返送ほか)は読み上げ対象外。将来は `sheet → parser` の対応表を足す形で追加する(`buildTable` は `{id, cycle, heading, expected, mixed}` のレコード列だけを受け取る)。

### 区分見出しの扱い
| 見出し | 扱い |
|---|---|
| 単一区分で時間範囲あり(例 `16-18時指定`) | 期待時間帯 16:00-18:00 を持つ。**ただし見出しが個別荷物の予定時間と同じ意味かは未確定(§9.2)** |
| 複数区分が混在(例 `AM指定・14-16指定・BC`) | 混在 (mixed)。期待値なし。**見出しだけで矛盾とは断定しない** |
| 範囲なし (例 `AM指定`) | 期待値なし |

## 3. 照合キー
- キーは Tracking ID(正規化後)の完全一致。DA番号 = Tracking ID とは仮定せず、スキャン値側で次の順に解決する。

| 順 | 条件 | matchKind |
|---|---|---|
| 1 | 正規化後が `[A-Z]{2}\d{10}` と完全一致 | exact |
| 2 | 設定した接頭辞/接尾辞(`allowedAffixes`)を除くと完全一致 | affix |
| 3 | 英数字以外で区切られたID形式トークンがちょうど1種類 | embedded |
| — | 異なるIDトークンが複数 | ambiguous → 読み上げない |
| — | それ以外 | not_found |

- 英数字が隣接する場合(`XDA…`, `DA…3`)、桁欠け、別接頭辞(`DB…`)は一致させない。
- 実機バーコードの形式は未確認。サンプル確認後に `allowedAffixes` を設定する。
- 既存 `lookupDA` の「含まれていれば一致」ロジックは使わない。

## 4. 状態判定

結果 status は `window` / `no_window` / `unknown` の3種。判定は上から順に最初に当たったもの。

| 順 | 条件 | status | reason |
|---|---|---|---|
| 1 | エリミにもSRにも無い | unknown | not_found |
| 2 | SRにあるがエリミに無い (`requireElimi` 既定true) | unknown | not_in_elimi |
| 3 | エリミにあるがSRに無い | unknown | not_in_sr |
| 4 | エリミで複数サイクルに重複 | unknown | dup_cycle_elimi |
| 5 | SR重複で時間帯・約束日が不一致 | unknown | dup_conflict_sr |
| 6 | 開始・終了とも空欄 | unknown (※) | time_blank |
| 7 | 片方のみ空欄 | unknown | time_partial |
| 8 | 形式不正・タイムゾーン付き・終了≦開始 | unknown | time_invalid |
| 9 | 開始日≠終了日 | unknown | date_span |
| 10 | Promised Delivery Date が空欄/不正 | unknown | date_promised_missing |
| 11 | 開始日≠Promised Delivery Date | unknown | date_mismatch |
| 12 | 基準日からの日数が許容範囲外 | unknown | date_out_of_range |
| 13 | 単一範囲見出しの期待値と異なる | unknown | conflict_elimi |
| 14 | 上記すべて問題なし | window | ok |

※ 空欄は常に unknown。空欄を「時間指定なし」に変換する経路は無い(旧 `noWindowEvidence` フックは廃止)。

SR重複: 同一ID・同一(開始,終了,約束日)なら1件に統合し重複件数に計上。1つでも異なれば dup_conflict_sr。
エリミ重複: 同一サイクル内の重複は無害(件数のみ計上)。複数サイクルにまたがる場合は dup_cycle_elimi。

### 4.1 確定ルール: 8:00〜22:00 = 時間指定なし (運用確定)
- SearchResults の開始が `08:00:00`、終了が `22:00:00`(秒は00、同日)に**完全一致**した場合、status は `no_window`。音声は `時間指定なし！`、画面ラベルは `時間指定なし`。
- 判定は §4 の順1〜13を**すべて通過した後**にだけ適用する(最後の順14の手前)。したがって次はすべて従来どおり除外される: 約束日と日付の不一致 / 当日・翌日の範囲外 / 日付またぎ / 約束日欠落 / SR重複で不一致 / エリミのCycle重複 / エリミ未掲載・SR未掲載 / 時刻不正 / 見出し矛盾(`conflict_elimi`)。
- 8:00〜22:00 以外の時間帯は変更しない(7:59〜22:00, 8:01〜22:00, 8:00〜21:59, 8:00〜22:01, 9:00〜22:00, 8:00〜23:00 などは通常の時間帯として読み上げ)。秒が00でない値も完全一致とみなさない。
- 結果は3種を明確に区別する: `window`(時間指定あり: 「8時から12時！」等)/ `no_window`(時間指定なし)/ `unknown`(確認できません)。
- 画面・集計・CSVでも `ok`(時間指定あり) / `no_window`(時間指定なし) / 各除外理由を別々に数える。「読み上げ可能」は ok + no_window。
- `noWindowRule` オプションで規則を差し替え可能(`null` は分析専用で、8-22を通常の時間帯として扱う)。本番(画面)は既定値を使う。
- エリミ見出しとの比較条件は今回の決定では変更していない(`headingCheck` 既定 true)。見出し矛盾による安全停止は維持。

## 5. 時間・日付仕様案(日付不整合 14 件への対応)

- 時刻は `YYYY-MM-DD HH:MM[:SS]` のゾーン無し壁時計。JST(現地時刻)として扱い、`Date` 変換はしない(ずれ防止)。`Z`・`+09:00` などが付いた値は推測せず time_invalid。
- 秒は切り捨て(23:59:59 → 23:59)。
- 読み上げ文は分が0なら `H時`、そうでなければ `H時M分`。`18:00-23:59` → `18時から23時59分！`。固定パターンは持たない。ただし 8:00-22:00 ちょうどは §4.1 により `時間指定なし！`。
- 日付の整合条件 (すべて満たすときのみ読み上げ):
  1. 開始日 = 終了日
  2. 開始日 = Promised Delivery Date
  3. 基準日(エリミの`日付`、または設定値)からの日数が `0〜+1`(当日・翌日)。範囲は `dateRange` で変更可、`null` で無効化。
- いずれかを満たさなければ除外(順9〜12)。画面には理由コードを出す。
- 実データ(SR全体で時間帯あり36行): 日付整合 20行 / 約束日≠開始日 16行(約束日が開始日より前 14行・後 2行)。エリミ対象内では 14行が date_mismatch。原因の解釈(再予約・SCC側の更新遅れ等)は未確定。

## 11. 仕様変更案A: エリミ見出しを「参考情報」に降格する (未適用・承認待ち)

背景: Cycle2「16-18時指定」はエリミ処理上の区分であり、個別荷物の配送希望時間ではない可能性が高い。運用で確認が取れるまで、本番は `headingCheck: true`(見出しと時間帯が異なる荷物は読み上げを停止)を維持する。

### 変更案
- 見出しと時間帯が異なっても読み上げを止めない。差異は画面に「参考: エリミ区分と異なる」と表示する(`headingDiffers`)。
- 実装は `headingCheck: false` と同じ(コード変更は不要。UI側で既定値を切り替え、`headingDiffers` を表示するだけ)。

### 安全条件への影響 (合成テスト `tests/delivery-window-heading-mode.test.mjs`、99組合せ)
SearchResults 19種 × エリミ 5種(Cycle1 / Cycle2 / Cycle2重複 / Cycle1+2 / 未掲載)の総当たりで確認。
- 各IDの除外理由は、現行から `conflict_elimi` を除いたものと完全に一致する。
- 結果が変わるのは「除外理由が `conflict_elimi` だけ」のIDのみ。それ以外の読み上げ可否・音声は現行と同一。
- 空欄 / 片方空欄 / 不正 / 逆転 / 日付不一致 / 日付またぎ / 約束日欠落 / 前日 / 遠い未来 / SR重複矛盾 / Cycle重複 / SR未掲載 / エリミ未掲載は、すべて停止のまま。
- 「時間指定なし」になるのは 08:00-22:00 ちょうどだけ。空欄は変換されない。
- 見出しとの差異は参考表示用に引き続き記録される。

### 実データでの影響 (参考、§10)
停止中の見出し矛盾16件のうち、案Aで読み上げ可能になるのは最大16件(時間指定なし11、時間指定あり5)。日付不一致などで停止している他の荷物には影響しない。

### 適用の条件(承認事項)
1. Cycle2 の見出しが個別荷物の希望時間ではないことの運用確認。
2. 画面に参考表示を出す文言の確認。
3. 適用は別コミット・別承認(本番は `headingCheck: true` のまま)。

## 12. Phase 4: スキャナー入力と男性音声 (画面未統合)

実装: `delivery-window-speaker.js`(音声出力)/ `delivery-window-scan.js`(スキャン制御・キー入力の組立)/ `delivery-window-voice.js`(男性声選択)/ `delivery-window-voice-check.html`(実機の音声確認ページ)。`index.html` と `lookupDA` は未変更。

### 12.1 結果の3区分
| 区分 | 条件 | 音声 | 画面ラベル |
|---|---|---|---|
| 時間指定あり (window) | 全安全条件を通過し、8:00〜22:00 以外の時間帯 | 「8時から12時！」など(データから生成) | 「8時から12時」+ `08:00〜12:00` |
| 時間指定なし (no_window) | 全安全条件を通過し、8:00〜22:00 ちょうど | 「時間指定なし！」 | 「時間指定なし」 |
| 確認不能 (unknown) | 上記以外すべて(空欄、日付不一致、範囲外、重複矛盾、見出し矛盾、未照合、データ未読込) | 「確認できません！」 | 「確認できません」+ 理由コード |

### 12.2 音声が重なったときの方式 (比較と推奨)
| 方式 | 動作 | 長所 | 短所 |
|---|---|---|---|
| キュー | 再生中は待ち、順番に読む | 取りこぼしなし | 連続スキャンで読み上げが遅れ、今持っている荷物と音声がずれる |
| 割り込み | 再生中を止めて新しい結果を読む | 常に今の荷物の結果 | 直前の結果が途中で切れる |
| 最新スキャン優先 | 割り込み+保留中の古い結果は破棄 | 1スキャン=1荷物の結果が常に最新と一致 | 同上(結果は画面で確認可) |

推奨・既定は**最新スキャン優先**(`policy:'latest'`)。作業者は荷物を1個ずつ手に持ってスキャンするため、遅れて古い荷物の結果を聞くより、常に今の荷物の結果を聞けることを優先する。切れた結果は画面に残る。`policy:'queue'`(上限3件、古いものから破棄)も実装済みで切替可能。同一商品の再スキャンは抑止せず毎回読み上げる。

### 12.3 失敗時の扱い
- 音声が使えない/例外/エラー/開始しない(2.5秒で監視)場合も、画面の結果は必ず返る(`spoke:false` と `speakFailReason` 付き)。例外は外に出さない。
- 音声OFFは失敗ではなく、通知しない。
- 男性声が端末に無い場合は日本語音声で代用し、`male:false` を返す(「男性声未検出」を表示する前提。男性と偽らない)。

### 12.4 入力
- 既存の `#scan-input`(キーボード入力型。Enter 終端、貼り付け、300ms 入力停止)を Phase 5 でそのまま使う。値は `lookupDA` のラッパーが受け取り、`DeliveryWindowScan.handleScan(raw)` に渡す。
- 独立入力口として `createKeyAssembler`(Enter/Tab 終端、任意のアイドル確定、最大長、Backspace/Escape、貼り付けは行単位)を用意。1回確定するたびに内部バッファを空にするため、前後の商品が混ざらない。
- 終端なしで2つのIDが連結された場合は、どちらの商品とも解釈せず「確認できません」(誤読より再スキャンを優先)。
- 接頭辞は `allowedAffixes` に設定したものだけ受け付ける(実機サンプル確認後に設定)。
- スキャン値は保持しない。履歴は区分・理由・ID末尾4文字のみ(最大20件)。

### 12.5 応答時間 (合成5,000行、20,000スキャン、偽の speechSynthesis)
| 区間 | p50 | p95 | 最大 |
|---|---|---|---|
| 検索 | 0.001ms | 0.001ms | 0.001ms |
| スキャン→`speak()` 呼び出し | 0.001ms | 0.002ms | 0.002ms |

照合テーブル構築(5,000行)は約29ms。**音声の再生開始(ブラウザ/OS側)は含まない**。実測は実機で `delivery-window-voice-check.html` の「開始までの時間」を見る。

### 12.6 男性音声の動作確認
- このコンテナ(ヘッドレス Chromium)には音声エンジンがなく、日本語音声 0 件・合成は `synthesis-failed`。**実際の発音・男性声の可否は未確認**。
- 確認ページ自体は動作し、音声が無い場合に「日本語音声がありません」と失敗理由を画面に表示することを確認した。
- 実機確認の手順: 現場端末のブラウザで `delivery-window-voice-check.html` を開き、「男性声を検出」と出るか、各フレーズが男性声で鳴るか、「開始までの時間」を記録する。
- 費用・通信: ブラウザ標準 `speechSynthesis` のみ。追加費用なし。OS内蔵(ローカル)音声は外部通信なし。`localService` が false の音声(一部のクラウド音声)は通信する可能性があるため、確認ページで `[通信あり]` と表示する。

## 13. Phase 5: 画面統合 (feat/scan-delivery-window-voice-clean、未デプロイ)

### 13.1 変更点
- `index.html`(挿入10行・削除0行・CRLF維持): 仕分けスキャンタブに `<div id="dw-root">` を1つ、ページ末尾に `delivery-window-*.js` 7本の読込を追加しただけ。`lookupDA` 本体、`speakRouteNumber`、`scanVoiceEnabled`、既存のイベント属性は無変更。
- `delivery-window-ui.js`(新規): 画面の描画と、`window.lookupDA` / `window.updateScanStatus` のラップ(1回だけ設置)。
- `delivery-window-session.js`(新規): 準備状態、2ファイルの読込、古い読込の無視、スキャン可否の判定(画面に依存しない)。

### 13.2 動作の分離
| | 時間帯モード OFF (既定) | 時間帯モード ON |
|---|---|---|
| `lookupDA` | 元の関数をそのまま呼ぶ(引数も同一) | 元の関数は呼ばない(既存の女性声・コース番号表示は動かない) |
| スキャン可否 | マニフェスト読込が必要(従来どおり) | エリミ報告書とSearchResultsの両方が正常に読み込めたときのみ |
| `#scan-ready`(入力欄) | 従来の条件で表示 | マニフェスト未読込でも表示。データ未読込中は入力欄を無効化し、必要なファイルを表示 |
| ドロップゾーン | 従来どおり | ON中は隠す(OFFに戻すと元の表示に復帰) |
- モードは毎回OFFで起動(保存しない)。ONにすると既存の音声は鳴らず、時間帯の読み上げだけが鳴る。
- OFFに戻すと、音声を停止し、`updateScanStatus` を呼んで元の表示条件に戻す。
- 既存コードに `updateScanStatus` が2つ定義されている(点呼用 `updateScanStatus(phase, driverName)` と仕分けスキャン用)。後の定義が有効になっている既存の状態であり、今回は変更していない。ラップは有効な方に対して、元の動作を実行した後に入力欄の到達性だけを補う。

### 13.3 データの読込
- 画面の2つのボタンから、エリミ報告書(.xlsx、シート「エリミネーション報告」)とSearchResults(.csv)を選択。ファイルはメモリ上でのみ扱い、保存も送信もしない。
- 読込が始まった時点で旧テーブルは使えなくなる(古いデータを黙って使わない)。ファイルが不正なら、エラーコードを表示してスキャン不可のまま(旧データは残さない)。
- 古い非同期処理: 同じ種類のファイルを続けて選んだ場合、最新の選択だけが有効。遅れて完了した古い読込(成功・失敗とも)は破棄される。
- 画面に最終更新を表示: データ読込時刻、SearchResults最終更新、基準日、エリミ対象件数・要確認件数。

### 13.4 表示と音声
- 結果カード: 時間指定あり(指定時間を表示・読み上げ)/ 時間指定なし(8:00〜22:00 完全一致のみ)/ 確認できません(理由・照合状態付き)。次のスキャンまで画面に残る。
- 履歴(最大10件): 時刻・区分・ID末尾4文字のみ。完全なTracking IDは画面にも保存にも出さない。入力欄はスキャン直後に空にする。
- 音声: ON/OFF切替、日本語音声の選択、男性声の有無を画面に表示(未検出・日本語音声なし・非対応は警告表示)。最新スキャン優先。音声が失敗・中断しても結果は画面に表示され、音声の状態欄に理由が出る。古い発話の遅れた終了・開始・エラーは最新の表示を変えない。
- 保存するのは音声ON/OFFと選択した音声名のみ(localStorage、失敗しても動作継続)。

### 13.5 入力経路 (既存の `#scan-input` を再利用)
- Enter・貼り付け: 確定したスキャンとして処理。値が短くても処理し、照合できなければ「確認できません」。
- 入力停止(約300ms)での自動確定: 12文字以上のときのみ処理。入力途中の短い値は処理せず、そのまま残す(途中入力で誤って「確認できません」と読み上げない)。

### 13.7 実機テスト手順 (現場端末)
準備: 本ブランチを本番と別の場所で開く(例: リポジトリで `python3 -m http.server 8080` を起動し、端末のブラウザで `http://<PCのIP>:8080/index.html`。CDNのため端末はインターネットに接続できること)。実データは使わず、まず合成ファイルで確認する。
1. `http://<PCのIP>:8080/delivery-window-voice-check.html` を開く。「男性声を検出」と出るか、各フレーズが男性声で鳴るか、「開始までの時間」(ms)を記録する。
2. `index.html` を開き「仕分けスキャン」タブへ。既定で「配送時間帯モード」がOFFであること、マニフェストを読み込んで従来どおり検索・コース番号の読み上げができることを確認する。
3. 「配送時間帯モード」をON。入力欄が無効で「データ未読込」と必要なファイルが表示されることを確認する。
4. エリミ報告書とSearchResultsを選択し、「✅ 使用可能」と最終更新が出ることを確認する。
5. バーコードスキャナーで荷物を1個ずつスキャンし、(a) 読み上げ内容と画面の一致 (b) 連続スキャン時に最新の結果だけが読まれること (c) 同じ荷物の再スキャン (d) 入力欄が毎回空になること、を確認する。
6. 実機バーコードの中身(接頭辞・終端キー)を記録する(接頭辞があれば `allowedAffixes` に設定する必要がある)。
7. 音声をOFFにしても結果が画面に出ること、ブラウザの音声を無効にした場合に警告が出ることを確認する。
8. モードをOFFに戻し、通常の検索と音声が従来どおり動くことを確認する。
実データでの読み上げ試験は、承認後に行う。
