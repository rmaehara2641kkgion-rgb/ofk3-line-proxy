# ローリングアラート API: 認証・保存・移行

対象: `GET /rolling-alerts/latest` / `POST /rolling-alerts/save`（氏名を含む結果を扱うため認証必須）

## 認証（既存OFK3方式の流用）
- 既存の `/tenko-sync` と同じ方式: **環境変数のトークン + リクエストヘッダー**、fail-closed。
  - トークン未設定 → `503`（データは返さない・書き込まない）
  - 不一致/無し → `401`（氏名等を含まない応答）
  - 同一IPから10分で20回失敗 → `429`
  - 比較は定数時間（SHA-256 ダイジェストの `timingSafeEqual`）
- 受け付けるトークン: `ROLLING_ALERT_TOKEN`（専用にしたい場合）または **既存の `TENKO_SYNC_TOKEN`**。どちらもソースには埋め込まない。
- ヘッダー: 既存画面が送る `X-Tenko-Sync-Token`、または `X-Rolling-Alert-Token`、`Authorization: Bearer`。
- 画面側のキーは既存の「点呼管理タブ → 端末間同期キー」（端末の `localStorage.tenkoSyncToken`）をそのまま使う。**新しい入力欄は追加していない。**

### 移行手順（既存画面を止めないために）
1. Render に `TENKO_SYNC_TOKEN` が**既に設定済み**なら追加作業なし。点呼同期キーを設定済みの端末は、そのままサーバー保存・復元が使える。
2. 未設定の場合: Render の環境変数に `TENKO_SYNC_TOKEN`（または `ROLLING_ALERT_TOKEN`）を設定し、各端末の同期キー欄へ同じ値を入力する。
3. 設定前・キー未入力の端末でも **画面の集計・一覧表示は従来どおり動く**。サーバー保存だけ行わず、画面に「同期キー未設定のためサーバー未保存」と表示し、結果はその端末のブラウザにのみ保存される。
4. 既に保存済みの結果は無い（これまで無認証APIの本番公開はしていない。main 未マージ）。移行すべき旧データはない。

## 保存データの検証（サーバー・復元時とも同じ `sanitizeSnapshot`）
- 既知の項目だけで作り直し（未知の項目は破棄）、文字列長・数値範囲・列挙値・日付形式（実在日）・件数上限（2000件）・本文サイズ（約1.5MB）を検査。
- 集計日時/データ投入日時は未来（端末時計のずれ10分超）・2020年より前を拒否。対象日は現在±400日。
- 不正なリクエストは 400/413 を返し、**既存の保存結果には触れない**（書き込みは一時ファイル→リネーム。失敗時はメモリも巻き戻す）。

## 保存と競合
- 最新1件のみ保存。サーバー採番のリビジョン（`ストアID.連番`）で競合を判定し、**端末の時計は新旧判定に使わない**。
- 保存時に「最後に見たリビジョン」を送る。違えば `409 conflict` で既存結果を返し、上書きしない。画面は「他端末の結果を表示」「この端末の結果で上書き保存」を選ばせる。
- 同一データ（指紋一致）の再投入は変更なし（リビジョンも不変、対象者の二重計上なし）。
- 画面からの保存は同時に1件のみ（連続投入での自己競合を防止）。

## 残存リスク
- **Render の一時ディスク**: 再デプロイ/再起動で保存ファイルが消える（既存の点呼同期と同じ制約）。消えた場合は、同じブラウザの保存から自動再保存する。ブラウザ保存も無い端末の結果は復元できない（Excel の再投入が必要）。恒久化には Render の永続ディスクまたは GAS/外部ストアが必要（要判断）。
- ファイル消失後は新しいストアIDになるため、古いリビジョンを持つ別端末は競合表示になる（黙って上書きしない）。
- 共有キー方式のため、利用者・端末の個別識別や監査ログはない（既存方式と同等）。
- `/rolling-alerts/*` は CORS 既定（`*`）だが、認証ヘッダー必須のため他サイトのページからは読み取れない。
